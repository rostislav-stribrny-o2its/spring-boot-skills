# API Contract-First

The contract is the shared base of backend and frontend. It is **contract-first**, but nobody
— human or AI — edits the OpenAPI document by hand. The document is the **output** of a typed
API model written in Java, which the compiler and tests check. From the document, the backend
and the frontend generate their code.

```
<module>-api-model        Java: Api… types + endpoint interfaces (annotations only, no logic)
      │  build: export without starting the application (approach to be confirmed by a prototype)
      ▼
specs/<app>/openapi/<visibility>/<area>/<module>-service-<visibility>.json   (committed)
      │  build: openapi-generator
      ├──────────────► backend module: generated controllers + …Dto (target/, not committed)
      └──────────────► frontend: generated TypeScript types/client per module
```

## 1. Where the contract lives

- **API model module** (`<module>-api-model`): Java classes `Api…` with swagger-core annotations
  (`@Schema`, `@ArraySchema`, `oneOf` + discriminator, `enumAsRef`) and annotated endpoint
  interfaces without logic. This is the only place where the API is authored.
- **Generated spec, committed** under
  `specs/<application>/openapi/<public|internal|server>/<area>/<module>-service-<…>.json`:
  - `public` — the public interface (for example used by the frontend);
  - `server` — reachable inside the company infrastructure;
  - `internal` — only within the same application.
  Each module that exposes an interface has its own document, per visibility. Interfaces that are
  not OpenAPI (for example WSDL) get their own folder beside `openapi/`.
- The spec is regenerated by the build and committed; CI fails when the committed file differs
  from what the build produces (freshness check). A reviewer sees every API change as a diff of
  the spec.
- **OpenAPI 3.0.3.** Move to 3.1 only when the generators drop their beta status for 3.1.
- Generated Java and TypeScript are **never committed** (`target/generated-sources/…`).

**Unverified assumption — confirm with a prototype before it becomes a template.** The decided
direction is to export the document at build time without starting Spring. swagger-core's Maven
plugin does that, but it reads **JAX-RS** annotations (`@Path`, `@GET`, …) plus the swagger
annotations — not Spring MVC `@GetMapping`; Spring-annotated endpoints are normally documented by
springdoc, which starts a context. Open points for the prototype:
- how the endpoint interfaces in the API model declare paths and methods (JAX-RS annotations used
  only as declarations, or another export path);
- producing `openapi: 3.0.3` (swagger-core writes 3.0.x by default; the exact version may need a filter);
- `format: decimal` for `BigDecimal` and the `maximum` for `int64` IDs (a swagger-core
  `ModelConverter` or explicit `@Schema` attributes);
- generated output must pass G1 and G2 unchanged.

## 2. Number and ID types — decided by the database range

| Value class (DB model) | PostgreSQL | OpenAPI | Generated Java | TS |
|---|---|---|---|---|
| small integer | `integer` | `integer`, `int32` | `Integer` | `number` |
| **ID and ordinary large integer (default)** | `bigint` identity, `MAXVALUE 9007199254740991` | `integer`, `int64`, `maximum: 9007199254740991` | `Long` | `number` |
| integer above 2^53 | `numeric(p,0)` | `number`, `format: decimal` | `BigDecimal` (domain `BigInteger` via a mapper with `toBigIntegerExact()`) | lossless parser needed |
| exact decimal (money, areas, effort) | `numeric(p,s)` | `number`, `format: decimal` | `BigDecimal` | `number` for display; exact computation in the backend or a lossless parser |
| measured value, no exactness claim | `double precision` | `number`, `double` | `Double` | `number` |

- Only standard OpenAPI types with the generator's **default mapping** — no `typeMappings` for
  numbers, never numbers as `string`.
- IDs are numbers in JSON, never strings.

## 3. Operations and naming

- `operationId` is readable camelCase, verb + noun (`listResourceRequests`, `createOrder`) — the
  generators turn it into method names.
- If the project documents design elements, every operation carries the element ID in an allowed
  extension (for example `x-des-id`); CI compares the documentation anchor with the generated spec
  by that ID. Production code carries no requirement or design IDs.
- English names in the contract; descriptions in the language the project's documentation uses.
- `tags` group operations into the generated interfaces (one interface per tag).

## 4. Shape of the API

- **Reads are data-oriented**: general enough that the frontend composes screens from them.
- **Writes are service-oriented**: operations on the domain (`confirmOrder`), not generic
  updates of table rows.
- Overview screens get **bulk or screen-shaped operations** instead of item-by-item and
  detail-by-detail loading — balanced, without one endpoint per widget.
- The backend prepares and reduces data; never ship tens of megabytes to the browser; assume a
  slower link between frontend and backend than between backend and database.
- The API may differ significantly from the database schema; both derive from the logical model,
  neither is generated from the other.

### URLs and statuses

- Plural, kebab-case resources: `/api/orders`, `/api/order-items`; nesting at most two levels.
- No success envelope: a response is the resource or a page object defined in the model.
- Errors are RFC 9457 Problem Details (`application/problem+json`, see `be-problem-details-rfc9457`);
  every operation declares its error responses in the model.

| Scenario | Status |
|---|---|
| read found | 200 |
| created | 201 (+ `Location`) |
| updated | 200, or 204 without body |
| deleted | 204 |
| validation failed | 400 |
| not authenticated / invalid token | 401 |
| authenticated, not allowed | 403 |
| not found | 404 |
| conflict (duplicate, optimistic lock) | 409 |
| unexpected | 500 |

### Pagination

- A page object in the model (`content`, `page`, `size`, `totalElements` or `hasNext`); cap
  `size` in the model (`maximum`) and in the backend.
- Sort fields from an allowlist, always with an ID tie-breaker.
- Large or frequently scrolled lists use keyset pagination (`after=<id>`), not deep offsets.

### Versioning

Request versioning is configured centrally with Spring Framework 7 and declared in the contract —
see `be-api-versioning`.

## 5. Code generation (backend)

```xml
<plugin>
    <groupId>org.openapitools</groupId>
    <artifactId>openapi-generator-maven-plugin</artifactId>
    <version>${openapi-generator.version}</version> <!-- pinned in the parent POM: a current 7.x with useSpringBoot4/useJackson3 (verify) -->
    <executions>
        <execution>
            <goals><goal>generate</goal></goals>
            <configuration>
                <inputSpec>${specs.dir}/app/openapi/public/core/core-service-public.json</inputSpec> <!-- specs.dir: see maven-reactor -->
                <generatorName>spring</generatorName>
                <apiPackage>com.example.app.core.api.generated</apiPackage>
                <modelPackage>com.example.app.core.api.generated.model</modelPackage>
                <modelNameSuffix>Dto</modelNameSuffix>          <!-- OrderDto: no clash with domain Order -->
                <configOptions>
                    <delegatePattern>true</delegatePattern>    <!-- hand-written code only in the delegate -->
                    <interfaceOnly>false</interfaceOnly>
                    <skipDefaultInterface>false</skipDefaultInterface> <!-- required with delegatePattern -->
                    <useSpringBoot4>true</useSpringBoot4>
                    <useJackson3>true</useJackson3>
                    <useBeanValidation>true</useBeanValidation>
                    <useTags>true</useTags>
                    <openApiNullable>false</openApiNullable>
                    <dateLibrary>java8</dateLibrary>
                </configOptions>
                <!-- not generateSupportingFiles=true: it adds a second @SpringBootApplication -->
                <supportingFilesToGenerate>ApiUtil.java</supportingFilesToGenerate>
                <output>${project.build.directory}/generated-sources/openapi</output>
            </configuration>
        </execution>
    </executions>
</plugin>
```

- The generator version and every option are pinned in the parent POM (one place); never
  `skipValidateSpec`.
- The frontend generates its TypeScript per module from the same committed spec.

## 6. Implementing the delegate

The generated controller calls an `…ApiDelegate`. The implementation is the **API adapter**:
it maps `…Dto` ↔ domain with a MapStruct `…ApiMapper` and calls exactly one service method.
No business logic, no transactions, no repositories here.

```java
@Component
public class OrdersApiDelegateImpl implements OrdersApiDelegate {

    private final OrderService orderService;
    private final OrderQueryService orderQueries;
    private final OrderApiMapper mapper;

    public OrdersApiDelegateImpl(OrderService orderService, OrderQueryService orderQueries,
                                 OrderApiMapper mapper) {
        this.orderService = orderService;
        this.orderQueries = orderQueries;
        this.mapper = mapper;
    }

    @Override
    public ResponseEntity<OrderDto> createOrder(CreateOrderDto body) {
        Order order = orderService.createOrder(mapper.toCommand(body));
        return ResponseEntity.status(HttpStatus.CREATED).body(mapper.toDto(order));
    }

    @Override
    public ResponseEntity<OrderPageDto> listOrders(Integer page, Integer size) {
        return ResponseEntity.ok(mapper.toPageDto(orderQueries.listOrders(page, size)));
    }
}
```

With `skipDefaultInterface=false` every operation the delegate does not override answers
`501 Not Implemented`. If the delegate bean is missing or not picked up, the generated controller
falls back to a no-op delegate and **every** operation answers 501. A contract test per operation
catches both.

## 7. Guards (all must be green in `mvn verify` and CI)

| ID | Guard | Catches |
|---|---|---|
| G1 | Lint of the generated spec (Spectral profile "Java-compatible OpenAPI"): `$ref` instead of inline objects, `type` on every property, `integer` with `format`, `int64` with `maximum` ≤ 2^53−1, `number` with `format` `decimal`/`double`, `array` with typed `items`, `oneOf` only with `discriminator` + `mapping`, no `anyOf`, enums as components, `operationId` required, allowed `x-` extensions only | constructs the generator turns into `Object`, empty interfaces or strings |
| G2 | Generate and compile Java (and TS) from the spec; ArchUnit over generated classes: no `Object`/`Map<String,Object>` properties, `decimal` → `BigDecimal`, `int64` → `Long` | what the linter cannot see |
| G3 | Generator configuration pinned (version, options, normalizer rules, templates) | drift between modules |
| G4 | `oasdiff breaking` against the last released spec | silently broken clients |
| G5 | Committed spec is fresh (build output = committed file) | backend and frontend drifting apart |
| G6 | Agent rules: AI writes only the API model classes; never the spec, never generated code | AI editing outputs |

ArchUnit tests over the API model enforce the authoring patterns (every `List` annotated with its
item schema, enums with `enumAsRef`, polymorphic bases with a discriminator, no raw `Object`).

## Opereta

- One interface: module `be`, visibility `public`, spec `specs/opereta/openapi/public/be/be-service-public.json`.
- Every operation carries **`x-des-id: DES-<MOD>-NNNNN`** (ID of the design element in the
  technical specification, five digits); the API model makes it mandatory, the linter checks its
  shape, CI compares the documentation anchor with the spec by this ID.
- Names in the contract are English; descriptions are Czech (application documentation language).
- The frontend reads nothing from the token; identity, roles and display permissions come from
  `/api/me` (see `be-oauth2-resource-server`).

## Gotchas
- Agent edits the OpenAPI JSON/YAML by hand — change the API model and rebuild
- Agent writes `api/openapi.yaml` or `src/main/resources/openapi.yaml` as the source of truth — the source is the API model; the spec lives under `specs/…` and is generated
- Agent puts ID fields as `string`/`uuid` or numbers without `format` — IDs are `integer/int64` with `maximum`
- Agent adds `typeMappings` for numbers — use the standard types; G2 checks the mapping
- Agent modifies generated controllers or models — implement the delegate; regenerate instead of editing
- Agent puts business logic or `@Transactional` in the delegate — the delegate maps and calls one service method
- Agent annotates the delegate with `@Service` — it is an API adapter (`@Component`); `@Service` is for business logic
- Agent sets `skipDefaultInterface=true` with `delegatePattern=true` — the generated controller stops compiling
- Agent sets `generateSupportingFiles=true` — a second `@SpringBootApplication` breaks repackaging
- Agent commits generated Java/TS — only the spec is committed
- Agent wraps responses in a success envelope or invents an error format — plain resources, Problem Details for errors
- Agent uses OpenAPI 3.1 features — the contract is 3.0.3
- Agent creates one endpoint per frontend widget — bulk or screen-shaped operations, without an explosion of endpoints
